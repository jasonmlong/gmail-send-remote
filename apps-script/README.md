# gmail-send Apps Script API

A lightweight Apps Script project that turns any Google account into a drafting endpoint for an AI agent. It contains the same renderer as the Node library (`GmailSendCore.js`, generated by `npm run build:apps-script`), reads the account's real signature from Gmail settings, learns the timezone from the user's calendar, and writes Gmail-identical drafts through the Advanced Gmail Service. No Cloud OAuth client, no payments, no tiers.

## Files

| File | Purpose |
|---|---|
| `appsscript.json` | Scopes, Advanced Gmail Service, web app settings |
| `Api.js` | `doGet` / `doPost`, token check, action table |
| `GmailAdapter.js` | Profile, threads, messages, signatures, drafts |
| `Drafting.js` | `draftReply`, `draftNew`, `draftForward`, `redraft` (render in-script) |
| `Setup.js` | `setup()`, `rotateToken()`, `setAllowSend()`, `selfTest()`, `testDraftLatestInbox()` |
| `GmailSendCore.js` | Generated bundle of `src/core` (do not edit) |

## Install into an account (about five minutes)

1. `npm run build:apps-script` in the repo root to produce `GmailSendCore.js`.
2. Go to script.google.com while signed in as the account, create a new project, and paste in each file above (or `clasp push` from this folder with a `.clasp.json` pointing at the script id). In Project Settings, tick "Show appsscript.json" and replace its contents with the one here.
3. Run `setup()` from the editor. Approve the consent screen (Gmail modify, Gmail settings, Calendar read-only). The log prints the token and the `.env` lines.
4. Deploy > New deployment > Web app. Execute as: Me. Who has access: Anyone. Copy the `/exec` URL.
5. In `gmail-send/.env` set `GMAIL_SEND_PROVIDER=appsscript`, `GMAIL_SEND_APPS_SCRIPT_URL`, `GMAIL_SEND_APPS_SCRIPT_TOKEN`. The MCP server and CLI now draft into that account.
6. Optional: run `testDraftLatestInbox()` to put one test draft into the newest inbox thread and compare it with a hand-typed reply in Gmail.

Each account gets its own copy of the script and its own token. That is what "add to any account" means here: the script runs as the account owner, so the agent never holds Google credentials.

## Calling it directly (no Node needed)

```
POST https://script.google.com/macros/s/<id>/exec
Content-Type: text/plain;charset=utf-8

{"token":"<token>","action":"draftReply","threadId":"18f...","body":"Hey Priya,\n\nGo ahead.\n\nThank you!"}
```

Response: `{"ok":true,"result":{"draftId":"r-...","threadId":"18f...","subject":"Re: ...","to":[...],"text":"..."}}`. The full action list is in `docs/APPS-SCRIPT-API.md`. Apps Script answers with a 302 to `script.googleusercontent.com`; follow redirects.

## Security notes

Reviewed adversarially before first deployment; findings and fixes are in [../docs/SECURITY-REVIEW.md](../docs/SECURITY-REVIEW.md).

- **A token is the only guard.** Anyone holding the URL and a live token can do what that token permits. Treat one like a password and revoke it if it is ever pasted, screenshotted or logged. The unauthenticated `GET` deliberately reveals nothing but the product name, so finding the URL does not tell an attacker whose mailbox it is.
- **Give each consumer its own token, scoped to what it needs.** `mintDraftOnlyToken()` produces one that can read and draft but cannot send or change settings, and that limit is fixed at mint time rather than depending on a switch. Revoke one with `revokeTokenByLabel()` without disturbing the others. Tokens are stored hashed, so the script properties hold nothing usable, and a minted token is shown exactly once.
- **Two capabilities are additionally off by default** and can only be armed from the editor: sending (`setAllowSend`) and writing the Gmail signature (`setAllowSettingsWrite`). Both gates must pass, so arming one globally does not grant it to a token that was not minted with it. Deleting drafts the API did not create is always refused, with no switch.
- **Narrow what it can read** with `setSearchScope('-in:spam -in:trash newer_than:180d')`. The scope is enforced inside the script, so it binds direct callers and not merely the Node client.
- **Raw messages are filtered.** A submitted raw message may only carry the headers the renderer itself produces, so the token does not confer arbitrary header control over a staged draft.
- **Scopes are the minimum for the job**: `gmail.modify` (read threads, write drafts), `gmail.settings.basic` (read the signature), `calendar.readonly` (timezone). Note that no Gmail scope allows drafting while forbidding sending, which is why the send switch is application-level. If the Calendar scope is unwanted, remove it from `appsscript.json` and the script falls back to the project timezone.
- **What this does not prevent.** An agent steered by a malicious email can still stage a convincing draft, including a forward of a sensitive thread, addressed to whoever the attacker wants. It cannot send it. Read the draft's recipients before you press Send; the drafting tools flag any recipient whose domain is new to the thread.
- Publishing as a Marketplace add-on would let users install with one click but requires Google's OAuth verification for the sensitive Gmail scopes. The per-account copy avoids that entirely.
