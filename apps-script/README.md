# gmail-send Apps Script API

A lightweight Apps Script project that turns any Google account into a drafting endpoint for an AI agent. It contains the same renderer as the Node library (`GmailSendCore.js`, generated by `npm run build:apps-script`), reads the account's real signature from Gmail settings, learns the timezone from the user's calendar, and writes Gmail-identical drafts through the Advanced Gmail Service. No Cloud OAuth client, no payments, no tiers.

## Files

| File | Purpose |
|---|---|
| `appsscript.json` | Scopes, Advanced Gmail Service, web app settings |
| `Api.js` | `doGet` / `doPost`, token check, action table |
| `GmailAdapter.js` | Profile, threads, messages, signatures, drafts |
| `Drafting.js` | `draftReply`, `draftNew`, `draftForward`, `redraft` (render in-script) |
| `Setup.js` | `setup()`, `rotateToken()`, `setAllowSend()`, `selfTest()`, `testDraftLatestInbox()` |
| `GmailSendCore.js` | Generated bundle of `src/core` (do not edit) |

## Install into an account (about five minutes)

1. `npm run build:apps-script` in the repo root to produce `GmailSendCore.js`.
2. Go to script.google.com while signed in as the account, create a new project, and paste in each file above (or `clasp push` from this folder with a `.clasp.json` pointing at the script id). In Project Settings, tick "Show appsscript.json" and replace its contents with the one here.
3. Run `setup()` from the editor. Approve the consent screen (Gmail modify, Gmail settings, Calendar read-only). The log prints the token and the `.env` lines.
4. Deploy > New deployment > Web app. Execute as: Me. Who has access: Anyone. Copy the `/exec` URL.
5. In `gmail-send/.env` set `GMAIL_SEND_PROVIDER=appsscript`, `GMAIL_SEND_APPS_SCRIPT_URL`, `GMAIL_SEND_APPS_SCRIPT_TOKEN`. The MCP server and CLI now draft into that account.
6. Optional: run `testDraftLatestInbox()` to put one test draft into the newest inbox thread and compare it with a hand-typed reply in Gmail.

Each account gets its own copy of the script and its own token. That is what "add to any account" means here: the script runs as the account owner, so the agent never holds Google credentials.

## Calling it directly (no Node needed)

```
POST https://script.google.com/macros/s/<id>/exec
Content-Type: text/plain;charset=utf-8

{"token":"<token>","action":"draftReply","threadId":"18f...","body":"Hey Priya,\n\nGo ahead.\n\nThank you!"}
```

Response: `{"ok":true,"result":{"draftId":"r-...","threadId":"18f...","subject":"Re: ...","to":[...],"text":"..."}}`. The full action list is in `docs/APPS-SCRIPT-API.md`. Apps Script answers with a 302 to `script.googleusercontent.com`; follow redirects.

## Security notes

Reviewed adversarially before first deployment; findings and fixes are in [../docs/SECURITY-REVIEW.md](../docs/SECURITY-REVIEW.md).

- **A token is the only guard.** Anyone holding the URL and a live token can do what that token permits. Treat one like a password and revoke it if it is ever pasted, screenshotted or logged. The unauthenticated `GET` deliberately reveals nothing but the product name, so finding the URL does not tell an attacker whose mailbox it is.
- **Give each consumer its own token, scoped to what it needs.** `mintDraftOnlyToken()` produces one that can read and draft but cannot send or change settings, and that limit is fixed at mint time rather than depending on a switch. Revoke one with `revokeTokenByLabel()` without disturbing the others. Every token, including the primary one, is stored only as a SHA-256 hash and shown exactly once, so a dump of the script properties yields nothing usable. Lost the primary? `rotateToken()`. Re-running `setup()` never reprints it and never revives a revoked one.
- **Two capabilities are additionally off by default** and can only be armed from the editor: sending (`setAllowSend`) and writing the Gmail signature (`setAllowSettingsWrite`). Both gates must pass, so arming one globally does not grant it to a token that was not minted with it. Updating or deleting a draft the API did not create is always refused, with no switch. Both matter together: updating used to mint the ownership record that deletion accepts, so an update was a way to launder a hand-written draft into a deletable one.
- **Narrow what it can read** with `setSearchScope('-in:spam -in:trash newer_than:180d')`. The scope is enforced inside the script, so it binds direct callers and not merely the Node client, and it applies to reads by thread or message id as well as to searches. Be precise about its reach: the operators enforced on an id read are `-in:spam`, `-in:trash` and `newer_than:`. Anything else in the scope string still narrows searching, but does not block a read by id.
- **Bcc is refused everywhere.** No action accepts it and the raw-message allowlist rejects the header. Gmail honours a Bcc present in a draft when a human later sends it and hides it from the visible copy, which is exactly how a staged draft becomes silent delivery to a third party.
- **Drafts are only visible to the token that made them.** `listDrafts` and `getDraft` return drafts this API created, so a credential cannot enumerate half-written personal mail.
- **Raw messages are filtered.** A submitted raw message may only carry the headers the renderer itself produces, so the token does not confer arbitrary header control over a staged draft.
- **Scopes are the minimum for the job**: `gmail.readonly` (read threads and messages), `gmail.compose` (create, update and delete drafts), `gmail.settings.basic` (read the signature), `calendar.readonly` (timezone), `userinfo.email` (identity).

  Two things about that list are worth understanding, because the consent screen is alarming and the reasons are not obvious.

  **No Gmail scope allows drafting while forbidding sending.** `gmail.compose` is the narrowest one that can write a draft at all, and Google describes it as "Manage drafts and send emails". That is why the send block is application-level instead: a token minted without the `send` capability cannot send, the global `setAllowSend` switch is off, and the MCP server does not register a send tool for such a token. Three independent gates, none of which is the OAuth scope.

  **`gmail.compose` replaces the broader `gmail.modify`** this project used to request, which also permitted relabelling, trashing and marking mail read. Nothing here does any of that. The cost of the narrower scope is that drafts go through the Advanced Gmail Service rather than `GmailApp`, whose draft methods ask for wider access; `GmailApp` still reads threads and messages, which `gmail.readonly` covers.

  `gmail.settings.basic` is what reads your real signature out of Gmail settings, which is the point of the project. There is no read-only variant, so the same scope that reads a signature could create filters. The script never does, and writing the signature needs both the `settings` capability and the `setAllowSettingsWrite` switch. If you would rather not grant it, capture the signature once into `config/signatures.json` and remove the scope from `appsscript.json`.

  If the Calendar scope is unwanted, remove it and the script falls back to the project timezone, at the cost of wrong times in the attribution line of every reply.
- **What this does not prevent.** An agent steered by a malicious email can still stage a convincing draft, including a forward of a sensitive thread, addressed to whoever the attacker wants. It cannot send it. Read the draft's recipients before you press Send; the drafting tools flag any recipient whose domain is new to the thread.
- Publishing as a Marketplace add-on would let users install with one click but requires Google's OAuth verification for the sensitive Gmail scopes. The per-account copy avoids that entirely.
